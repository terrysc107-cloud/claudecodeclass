Every product you build should have a way to charge for it. Adding Stripe to a Next.js app follows the same pattern every time — learn it once, apply it everywhere.

## The Pattern

1. Create a product and price in the Stripe dashboard
2. Build a checkout session API route
3. Build a success/cancel redirect handling
4. Build a webhook handler that grants access
5. Gate your features behind the access check

## Step 1: Install and Configure Stripe

```bash
npm install stripe @stripe/stripe-js
```

Use Cursor to set up the Stripe client:

```
@lib/stripe.ts Create a Stripe server-side client using the
STRIPE_SECRET_KEY environment variable. Export it as a singleton.
Follow the pattern in the Stripe Node.js docs.
```

## Step 2: Checkout Session API

```
@app/api/stripe/checkout/route.ts Build a POST endpoint that:
- Gets the current user from Supabase session
- Returns 401 if not authenticated
- Creates a Stripe checkout session for price ID: [your price ID]
- Sets success_url to /dashboard and cancel_url to /
- Returns the session URL
```

Review the diff. Make sure the user ID is being passed in the session metadata — you'll need it in the webhook.

## Step 3: The Webhook

This is where payment confirmation happens. Never trust the redirect URL.

```
@app/api/stripe/webhook/route.ts Build a webhook handler that:
- Verifies the Stripe signature using STRIPE_WEBHOOK_SECRET
- Handles the checkout.session.completed event
- Extracts the user_id from session metadata
- Inserts a record into the user_purchases table
  (user_id, stripe_session_id, created_at)
- Returns 200 on success

@lib/supabase/server.ts Use the service role client for the
database insert (bypasses RLS).
```

<Callout type="warning">
The webhook signature verification is non-optional. Without it, anyone can send a fake webhook to your endpoint and grant themselves access. Cursor will generate it correctly if you ask — just make sure the `STRIPE_WEBHOOK_SECRET` environment variable is set in both your local `.env.local` and in Vercel.
</Callout>

## Step 4: Access Gating

Check purchases in your middleware or page:

```
@proxy.ts Add a check that redirects to / with ?upgrade=true
if the user visits /dashboard/* but has no record in user_purchases.
@lib/progress.ts Add a hasAccess(userId) function that queries
user_purchases for a record matching the userId.
```

## Testing Locally

Use Stripe CLI to forward webhooks to localhost:

```bash
stripe listen --forward-to localhost:3000/api/stripe/webhook
```

Use Stripe's test card numbers (4242 4242 4242 4242) for test purchases.

<Callout type="tip">
Always test the full checkout flow before deploying: click the buy button, complete checkout with a test card, verify the webhook fires, verify the database record is created, verify the user can access the gated content. This 5-minute test prevents the worst possible outcome: customers paying and not getting access.
</Callout>

## The Same Pattern Every Time

Once you've built this once, it's a template. Every subsequent product gets Stripe integration in under 30 minutes. That's the compounding value of learning the pattern well the first time.

<KeyPoint>Every product you build should have a way to charge for it. The Stripe + webhook pattern is the same every time — learn it once and apply it to everything. Never trust redirect URLs for payment confirmation; webhooks are the source of truth.</KeyPoint>
