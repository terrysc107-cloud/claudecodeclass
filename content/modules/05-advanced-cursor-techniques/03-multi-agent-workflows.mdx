Once you're comfortable with Claude Code's core workflows, you can start using it as an orchestrator that spawns sub-agents for parallel work — one for the backend, one for the frontend, one for tests. This is how you move at a pace that would otherwise require a small team.

## How Claude Code Agents Work

Claude Code can spawn sub-agents using the Agent SDK. Each sub-agent runs as an independent Claude session with its own context window and tool access. The orchestrating session assigns tasks, the sub-agents execute them, and the orchestrator reviews and integrates the results.

This is not just running multiple terminal windows manually — it's a programmable coordination layer where the main Claude session reasons about which tasks can run in parallel and manages the flow.

```
You are an orchestrator. I need to build a Stripe integration.
Spawn two agents:
- Agent 1: Build POST /api/checkout/route.ts — creates a Stripe
  checkout session. Reference the pattern in app/api/payments/route.ts.
- Agent 2: Build the PricingCard component at components/PricingCard.tsx
  that calls /api/checkout on click. Match button styles in components/ui/.

Run them in parallel. Report back when both are complete with a summary
of what each agent built and any integration points to review.
```

<Callout type="tip">
This workflow shines when you have genuinely independent work. "Build the API route" and "build the UI component" can happen in parallel because they don't share in-progress state. "Build the data model" and "build the API that uses it" cannot — do those sequentially.
</Callout>

## Choosing What to Parallelize

Work is parallelizable when:
- The two tasks don't share in-progress state (both can start from current committed code)
- A failure in one task doesn't require changes in the other
- Each task has a clear, independent specification

Work must be sequential when:
- Task B depends on the output of Task A
- Both tasks modify the same files
- You need to review Task A before you can write the spec for Task B

## The Orchestrator Pattern

The most effective multi-agent setup has a clear hierarchy:

**Orchestrator session:** Holds the high-level plan, assigns tasks, reviews outputs, handles integration. This is where you interact.

**Worker agents:** Each receives a focused, self-contained task. They don't need to know about each other — only about the code they're touching and the interfaces they must conform to.

The orchestrator is also responsible for writing the interface contracts before spawning workers:

```
Before spawning agents, define the API contract:
- POST /api/checkout accepts: { priceId: string }
- Returns: { url: string } on success, { error: string } on failure
- Auth: requires active session, returns 401 if not authenticated

Now spawn Agent 1 to implement the route and Agent 2 to implement
the UI — both working to this contract.
```

<Callout type="info">
Your role in multi-agent workflows is not just reviewing output — it's ensuring coherence. After sub-agents complete their tasks, have the orchestrator run an integration check: "Agent 1 built the API, Agent 2 built the component. Are they consistent? Do the request shapes and response handling match?" This catches integration assumptions before they ship.
</Callout>

## Single Session vs. Multi-Agent

Use a single session when:
- The task is linear and each step depends on the last
- The total work fits comfortably in one context window
- You want maximum coherence and minimal coordination overhead

Use multi-agent when:
- You have clearly independent parallel tasks
- The work is large enough that a single session would hit context limits
- You want to specialize each agent (one agent focused on backend patterns, one on frontend)
- You're running a structured process like a full feature build across several files

## After Parallel Work: Integration Review

After merging parallel agent outputs, always run a coherence check in the orchestrator session:

```
I just ran two parallel agents.
One built the checkout API route, one built the PricingCard component.
Read both files and tell me: are they consistent?
Do the data shapes, endpoint paths, and error handling match?
```

Then run tests. Parallel development creates integration assumptions — this review catches them before they become bugs.

<KeyPoint>Multi-agent orchestration with Claude Code lets you run parallel workstreams on independent tasks. The orchestrator defines contracts, assigns work, and verifies coherence. Keep tasks genuinely independent and always do an integration review after merging parallel outputs.</KeyPoint>
