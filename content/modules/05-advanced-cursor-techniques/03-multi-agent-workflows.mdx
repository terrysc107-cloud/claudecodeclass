Once you're comfortable with Cursor's core workflows, you can start running multiple Composer sessions in parallel — one for the backend, one for the frontend, one for documentation. This is how you move at a pace that would otherwise require a small team.

## The Setup

Cursor supports multiple windows. Each window can have its own active Composer session:

1. Open a new Cursor window (Cmd+Shift+N on Mac / Ctrl+Shift+N on Windows)
2. Open the same project in the new window
3. Each window runs its own Composer session with independent context

You become the orchestrator, reviewing and accepting output from multiple parallel streams.

<Callout type="tip">
This workflow shines when you have genuinely independent work to do. "Build the API route" and "build the UI component" can happen in parallel because they don't share in-progress state. "Build the data model" and "build the API that uses it" can't — do those sequentially.
</Callout>

## Choosing What to Parallelize

Work is parallelizable when:
- The two tasks don't share in-progress state (both can be based on the current committed code)
- A failure in one task doesn't require changes in the other
- Each task has a clear, independent spec

Work must be sequential when:
- Task B depends on the output of Task A
- Both tasks touch the same files
- You need to review Task A before you can write the spec for Task B

## A Practical Example

You're building a Stripe integration for a SaaS:

**Session 1:** "Build the Stripe checkout API route at `app/api/checkout/route.ts` using the pattern in `app/api/payments/route.ts`. Create a session for a one-time $97 payment."

**Session 2:** "Build the `PricingCard` component for the landing page that calls `/api/checkout` on click. Match the button style in the existing CTA components."

These are independent. Session 1 builds the backend. Session 2 builds the frontend. You review both diffs, accept them, and connect them in a third step.

<Callout type="info">
Your role in multi-agent workflows isn't just accepting output — it's ensuring coherence. After accepting parallel sessions, do a Chat review: "I just added two features. Are there any inconsistencies or integration issues I should be aware of?" Cursor will spot things you might miss when reviewing diffs in isolation.
</Callout>

## Integration Review

After merging parallel sessions, always run a coherence check:

```
@newly-changed-files I just ran two parallel Composer sessions.
One built the checkout API, one built the PricingCard component.
Are they consistent? Do the data shapes and endpoint paths match?
```

Then run tests. Parallel development creates integration assumptions — this review catches them before they ship.

<KeyPoint>Parallelizing AI sessions is the new parallelizing developers — you're the orchestrator. The key is keeping tasks genuinely independent. One failed assumption in a parallel session is easier to fix than a tangled multi-file conflict.</KeyPoint>
