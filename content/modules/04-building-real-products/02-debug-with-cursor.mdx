Debugging is where developers lose the most time. A 30-second fix takes 45 minutes because finding the root cause is hard. With Claude Code, root cause analysis is fast — and the fix comes with an explanation so you understand what went wrong.

## The Debugging Workflow

**Step 1: Copy the error**

Copy the full error message and stack trace from your terminal, browser console, or test output.

**Step 2: Paste into Claude Code**

```
I'm getting this error when submitting the checkout form:

TypeError: Cannot read properties of undefined (reading 'id')
    at processPayment (lib/stripe.ts:47:28)
    at POST (app/api/checkout/route.ts:23:18)

Read lib/stripe.ts and app/api/checkout/route.ts and tell me
what's causing this error.
```

**Step 3: Ask for the root cause first**

```
What is causing this error? What is undefined and why?
```

**Step 4: Understand before fixing**

Read the explanation. Make sure it makes sense. Then ask:

```
What's the correct fix?
```

<Callout type="warning">
Don't skip the "understand" step. Applying a fix you don't understand is how technical debt accumulates and how bugs get fixed in one place only to reappear in another. The explanation takes 30 seconds to read. That's not optional.
</Callout>

## Let Claude Run the Tests Directly

The most powerful debugging workflow in Claude Code is letting it run your tests and iterate:

```
Run `npm test` and fix any failures. Explain what each failure
was caused by before applying the fix.
```

Claude runs the tests, reads the failure output, traces the problem to the relevant source code, fixes it, and runs the tests again. It repeats this loop until the suite is green — or until it hits something that needs your input.

This is faster than copying error output back and forth manually.

## For Runtime Errors

Include the stack trace and any relevant state:

```
This error occurs when a user with no saved payment method
tries to resubscribe. Read lib/payments.ts.

The error is:
[paste error]

The `subscription` object at the point of the error looks like:
[paste relevant object or describe it]
```

The more context you give, the more accurate the diagnosis.

<Callout type="tip">
If you're not sure which files are involved, tell Claude what you were doing when the error occurred and let it search. "I got this error when creating an order — find the relevant files and diagnose it" is a valid prompt.
</Callout>

## For Test Failures

Paste the failing test output and reference the relevant files:

```
This test is failing. Read tests/users.test.ts and
app/api/users/route.ts. Here's the error output:

[paste output]

What's wrong?
```

<Callout type="tip">
When a test fails after an implementation session, don't assume the test is wrong. More often, the implementation missed something the test was designed to catch. Ask Claude to explain what the test is checking before deciding whether to fix the code or update the test.
</Callout>

## For TypeScript Errors

TypeScript errors are often verbose and hard to parse. Paste the full error and ask Claude to decode it:

```
Read types/api.ts and app/api/orders/route.ts.
I'm getting this TypeScript error and I don't understand
what it's telling me:

[paste error]

What does it mean and how do I fix it?
```

## Iterating to Resolution

Claude Code works best for debugging when you treat it as an interactive loop rather than a single question. If the first fix doesn't fully resolve the issue:

```
The fix resolved the original error but now I'm seeing this:
[new error]

Keep going.
```

Claude maintains context across the session and can keep iterating until the problem is resolved.

## The Speed Gain

Most developers spend the majority of debugging time in diagnosis. With Claude Code, diagnosis is near-instant because Claude reads the actual source files rather than working from your description of them. The time investment shifts almost entirely to understanding and verification — which is exactly where your attention should be.

<KeyPoint>Always ask Claude to explain the bug before applying the fix. Understanding what was wrong makes you a better developer and prevents the same pattern from appearing elsewhere in your code. Better yet, let Claude run your tests directly and iterate to a green suite.</KeyPoint>
