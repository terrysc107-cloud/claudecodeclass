Tests are the thing developers know they should write more of and rarely do. With Cursor, writing a test suite for a function takes 30 seconds. There's no longer a time-cost excuse.

## Basic Test Generation

Open Chat, reference the function, and ask:

```
@src/lib/pricing.ts Write a comprehensive test suite for
the calculateDiscount function. Use Vitest. Cover:
- Standard discount calculation
- Zero-value inputs
- Maximum discount cap
- Invalid input types
```

Paste the output into your test file. Run. Fix failures.

<Callout type="tip">
Always ask specifically for edge cases. The default test generation covers the happy path. The valuable tests — the ones that catch real bugs — are the ones for empty inputs, null values, boundary conditions, and error states. Ask for those explicitly.
</Callout>

## Integration Tests

For API routes and more complex flows, give Cursor the full context:

```
@app/api/orders/route.ts @lib/stripe.ts @lib/supabase/server.ts
Write integration tests for the POST /api/orders route.
Test:
- Successful order creation with valid payment
- Failed payment (Stripe error)
- Missing required fields
- Unauthenticated request
- Database write failure

Mock Stripe and Supabase. Use Vitest.
```

The key is providing all the relevant files so Cursor understands the dependencies.

## When Tests Fail

Generated tests sometimes fail, especially integration tests where the mocking setup is complex. Don't immediately ask for a fix. First:

```
@tests/orders.test.ts This test is failing: [paste output].
Can you explain what the test is checking and what
specifically is going wrong?
```

Understanding the failure tells you whether the test is wrong (needs updating) or the source code is wrong (needs fixing). They're different problems.

<Callout type="info">
Sometimes a Cursor-generated test reveals a real bug in your code. The test is correct, and it's correctly identifying a case your code doesn't handle. Before updating the test to pass, verify that the test expectation is actually what you want.
</Callout>

## Test-Driven Feature Development

An advanced workflow: write the tests before the implementation.

Ask Cursor to generate tests based on your spec:

```
Write tests for a validateOrderTotal function that:
- Accepts an order object with items array and total
- Verifies the total matches the sum of item prices
- Throws if total is negative
- Throws if items array is empty
```

Then use Composer to implement the function that makes all tests pass. This test-first approach produces tighter, more reliable code.

## Retrofitting Tests

For existing code without tests, attack it module by module:

```
@src/lib/utils.ts Write tests for all exported functions
in this file. Focus on functions that handle data transformation
or have conditional logic.
```

<KeyPoint>Tests you'd skip writing manually take 30 seconds with Cursor. Lack of test coverage is no longer a time problem — it's a habit problem. Make test generation a standard part of every feature delivery.</KeyPoint>
