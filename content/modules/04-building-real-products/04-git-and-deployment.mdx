Git hygiene matters more when you're working with clients, collaborating with a team, or building a codebase you'll return to. Claude Code handles the tedious parts of git — commit messages, PR descriptions, release notes — through the same bash tool it uses for everything else.

## Generating Commit Messages

Claude Code can run `git diff` directly and generate a commit message from the actual diff:

```
Run `git diff --staged` and write a concise, semantic commit
message for these changes. Use conventional commits format
(feat:, fix:, refactor:, etc.) Keep the summary line under
72 characters.
```

The output will be specific, professional, and accurate — because Claude read the real diff rather than your description of it.

<Callout type="tip">
Conventional commit prefixes: `feat:` for new features, `fix:` for bug fixes, `refactor:` for non-breaking code improvements, `docs:` for documentation, `test:` for test additions, `chore:` for maintenance. Using these consistently makes your git history scannable and helps automated tooling generate changelogs.
</Callout>

## Committing Directly

You can ask Claude Code to handle the entire commit:

```
Stage all the changes we made and commit them with an
appropriate conventional commit message.
```

Claude will run `git add`, generate a message based on what changed, and create the commit. Review the message before confirming if you want, or let it run and check with `git log` afterward.

## PR Descriptions

When creating a pull request, ask Claude to generate the description from the branch history:

```
Run `git log main..HEAD --oneline` to see the commits on this
branch. Then write a pull request description that covers:
- What changed and why
- How to test it
- Any migration steps needed
```

A clear PR description is a professional signal and makes code review faster for everyone involved.

<Callout type="info">
Claude Code can also create the PR directly using the GitHub CLI if `gh` is installed. Ask it to run `gh pr create` with the generated description. The entire PR creation workflow — branch, commits, description, and PR — can happen without leaving the terminal.
</Callout>

## Deployment Scripts

Ask Claude to write the deployment steps as a shell script:

```
Write a shell script that:
1. Runs the test suite and exits if any fail
2. Builds the Next.js app
3. Deploys to Vercel via the Vercel CLI
4. Runs a smoke test against the production URL
5. Sends a Slack notification on success or failure

Save it as deploy.sh and make it executable.
```

Claude writes the script, saves it, and makes it executable. You can run it as part of a CI pipeline or as a manual deploy step.

## Running Git Operations

Claude Code can run any git operation via the bash tool:

```
Show me the last 10 commits with their messages and authors.
```

```
Create a new branch called feature/notification-preferences
and switch to it.
```

```
Run `git stash` to save my current changes, then switch to
main and pull the latest.
```

This is useful for the mechanical parts of git that interrupt your flow — Claude handles them while you stay focused on the work.

## Release Notes

When shipping a new version to clients or users:

```
Run `git log v1.1.0..v1.2.0 --oneline` to see what changed
in this release. Then write user-friendly release notes for
version 1.2.0. Audience: non-technical business owners.
Keep it brief and focus on what changed from the user's perspective.
```

Client-facing release notes should be in plain language, not technical jargon.

<Callout type="info">
A client who receives clear, professional release notes with each deployment feels confident about the work being done. This small habit — two minutes per release — builds trust and reduces the "what did you actually change?" conversations.
</Callout>
